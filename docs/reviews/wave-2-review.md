# Wave 2 review: the system cookie jar is the only cookie store (D1)

Reviewed: the uncommitted working tree on top of `6462aa91` (Wave 1). `git status --short`: 14 modified files, 2 deleted (`SessionStore.kt`, `CookieLifecycleManager.kt`), 1 new source file (`shared/.../core/SystemCookieJar.kt`), 3 new test files under `FaselHDV2Provider/src/test/kotlin/com/cloudstream/shared/core/`. Read-only review; no gradle run (a build was in progress). Every line cited was read in the working tree, in `git diff`, or in `git show HEAD:` for deleted code. OkHttp behaviour is cited from the `okhttp-4.12.0-sources.jar` in the gradle cache (`BridgeInterceptor.kt`, `Cookie.kt`).

## Verdict

**Accept with fixes.** D1 is met: the four stores are down to one, every OkHttp client that fetches provider pages carries `SystemCookieJar`, the WebView engines' returned cookie maps are no longer merged anywhere in shared, and there is no `removeAllCookies` left in this repo. The deletions the spec lists are complete and the R3 non-touch list is intact (`DomainManager.kt` is not in `git diff --stat`; the `SessionProvider.kt` hunks remove only cookie code). Three things need attention before the commit is trustworthy: the media validator now sends a different `Cookie` than the player will when a CDN token and a stored cookie collide (F1), the pre-solve invalidation cannot reach a `Domain=`-scoped `cf_clearance`, which is the exact scope the spec assumes it has (F3), and the 10-second "fresh clearance, retry HTTP first" guard was deleted with nothing replacing it (F5). One provider regression is knowingly accepted and needs an on-device check (F2).

## Point-by-point judgements the reviewer was asked for

**1. `SystemCookieJar` correctness.** `loadForRequest` (`:51-58`) splits on `;`, trims, drops blanks, and hands each pair to `Cookie.parse(url, pair)`. A value containing `=` survives: `Cookie.parse` cuts at the first `=` (`Cookie.kt:373-379`). A segment without `=` returns null (`Cookie.kt:374`) and is dropped by `mapNotNull`, no exception. Null/blank header returns an empty list (`:53`). `saveFromResponse` (`:60-66`) writes `cookie.toString()` against the response URL; `Cookie.toString` (`Cookie.kt:214-246`) reproduces `expires=`/`max-age=0`, `domain=` only when not host-only, `path=`, `secure`, `httponly` — verbatim enough that `CookieManager` decides scope, which is the spec's requirement. `AndroidCookieStorage` (`:24-41`) is a stateless object; `CookieManager` is thread-safe; no shared mutable state was added. `expireCookiesFor`: scope of *names* is right (only names the store returns for that URL, `:75-79`); scope of the *write* is not (F3). `Path=/` is right only for root-path cookies; a cookie set with another path survives.

**2. Clients.** With the jar: `getRaw` (`ProviderHttpService.kt:263-270`), `executeDirectRequest` (`:716-720`), `executePostRequest` (`:832-836`), `DirectHttpStrategy` (`:78-82`, dead), `MediaUrlValidator` (`:116-117`, F1). `useSession` (`:242-248`) is "this host must see an anonymous request" — an unauthenticated CDN probe or a redirect hop where a stale cookie changes the answer; `NO_COOKIES` is the right jar for that, and no caller passes `false` today (grep). Deliberately without the jar and correct: `FaselHDExtractor.kt:180-184` (`NO_COOKIES`, manual `Cookie` from `CookieManager` at `:452`, `:479`, `Set-Cookie` written back by hand `:456`, `:480`); `Ipv4PinnedInterceptor.kt:29-42` (replays the player's request as-is, so it carries the link's `Cookie` header; a jar would overwrite it); `SnifferExtractor.kt:693-698` (headers already carry the store's cookie from `:349-359`; a jar would send the same string or, on a CDN host with its own cookie, overwrite it); `VideoSnifferEngine.kt:525-533` (manual read and write-back against `requestUrl`).
