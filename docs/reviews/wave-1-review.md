## Verdict

**Accept with fixes.** R1 is met. R2 is met on the four spec'd WebView tiers and the three OkHttp paths in `ProviderHttpService`, but one caller-supplied UA that a provider depends on is now silently ignored (F1), two loadUrl sites still send the detectable `X-Requested-With: ""` (F2), and one provider still ships a third hardcoded brand string (F3). All three are small.

## Accept-Encoding

The implementers' reasoning is correct. OkHttp's `BridgeInterceptor` adds `Accept-Encoding: gzip` and sets its transparent-gzip flag only when the request has neither `Accept-Encoding` nor `Range`; only then does it wrap the body in a `GzipSource` and strip `Content-Encoding`/`Content-Length`. A request that sets `Accept-Encoding` itself gets the raw compressed body back. `FingerprintInterceptor` is an application interceptor (`addInterceptor`, `ProviderHttpService.kt:385, :861, :984`), so it runs before `BridgeInterceptor`; its `user-agent` wins over OkHttp's default and its silence on `accept-encoding` leaves gzip handling to OkHttp. I cannot verify the `BridgeInterceptor.kt:66-72` line citation in `FingerprintInterceptor.kt:26` against the exact 5.0.0-alpha.12 source from here; the behaviour is right.

Deleted blocks: `SessionState.buildHeaders` (old `:78-98`), `executeDirectRequest` headers (old `:839-856`), `getRaw` identity (old `:382-386`), `StrategyRequest.buildHeaders` (old `:34-57`). None set `Accept-Encoding`. `MediaUrlValidator.kt:170` still sets `identity`, and it also sends `Range: bytes=0-0` (`:126`), which alone disables transparent gzip. `LazyExtractor.kt:336` still sets `gzip, deflate, br` on an `app.get`; untouched, pre-existing.
